AgentOffice

An AI office team you just tell what to do. It plans the spreadsheet work, writes the automation, tests it on your data, and asks before anything runs.

Team Automaters · Built on Zetaris, Meterless Nightshift and NVIDIA Nemotron

AgentOffice is an office team made of agents that you can simply tell what to do. Attach a spreadsheet and describe the repetitive work, and it plans the steps, writes the automation, tests it on your real data and asks you to approve the exact code before handing back the filled file. You can also ask it where your team's time goes, and it answers with evidence and proposes what to automate first.

Our user is a small office team: operations, finance or admin, with nobody whose job is automation. Their time goes into the same handful of manual steps, many times a day, spread across email, PDFs, spreadsheets and an ERP. Plenty of tools can automate a task once you know which task. What these teams lack is someone to find the routine, prove it is worth automating, build it, test it, and get it approved safely.

In our synthetic dataset, three systems describe the same work, invoice matching, and give three different answers: timesheets say 71.5 hours a week, the ticket system says 19.5, and the activity log measures 32.9 hours of hands-on time. The product is one pipeline with three stages, and each stage answers one of the three track challenges. Discover finds where the time goes across fragmented sources. Explain says why, with every number cited. Decide and Build, our primary track, picks what to automate, builds it, tests it and asks a human to approve. Thirteen agents share one World Model: every agent reads its context from it and writes back what it learns. H-MEM, a second engine, carries lessons and human decisions between runs.

This is the deepest loop, and the heart of Track 3. The PM ranks the routines the data revealed and writes a structured spec. Before that plan goes anywhere, a Priority Critic checks every claim against what the activity log measured and sends over-claims back. The Engineer writes code from the spec. QA tests it, and every failing case goes back to the Engineer, up to three revisions. The Manager decides behind a rule gate: it cannot approve code that failed QA. Finally a human approves the exact code, bound to its hash. Every arrow on this slide is a logged handoff.

QA tests the spec, never the code

1

The PM writes a spec, not prose

A small rule language: a key, ordered checks, and the statuses they lead to.

2

QA derives the expected results

From the spec alone: every branch, tolerance edges, case and spacing, ambiguous keys, and a renamed column that must fail loudly.

3

The code runs in a sandbox

Allowed imports only, no eval or file access, an empty environment and a hard timeout.

invoice_po_matcher

key: po_number (strip, upper)

check: vendor equals_ci → vendor_mismatch

check: amount within 1% → amount_mismatch

statuses: no_po · ambiguous_po · matched

Halve the tolerance in the code, and QA catches it. That case is in the test suite.

The key design decision. The PM does not hand the Engineer a paragraph; it writes a spec in a small rule language, a key plus ordered checks and statuses. Because the spec has exact meaning, QA computes the expected result for every test case from the spec alone, without looking at the code: every branch, values just inside and just outside a tolerance, case and spacing variants, ambiguous keys, and a renamed column that correct code must reject loudly. So QA cannot simply agree with buggy code. The code runs in a sandbox with an import whitelist, no eval or file access, an empty environment and a timeout. If you halve the tolerance in the code, QA catches it, and that case is in our test suite.

Session 1

Learns

The team proposes the invoice matcher. The finance manager rejects it: “ERP writes need my sign-off first.”

Session 2

Recalls

The Memory Keeper retrieves that decision. The PM proposes order-status replies instead.

Session 3

Acts on it

With that approved, it moves on to CRM dedupe. A Finance-only question escalates instead of asking again.

H-MEM, built to the Meterless reference: 8-signal retrieval with reasons, an approval boundary for new memories, conflicts resolved on the record, a hash-chained trust ledger. Tested end to end.

Agents that forget repeat their mistakes, so we built the Meterless H-MEM engine as the team’s long memory. In session one the team proposes the invoice matcher and the finance manager rejects it, with a reason. In session two the Memory Keeper retrieves that decision and the PM proposes order-status replies instead. In session three, with that one approved, the team moves on to CRM dedupe. And when the only option is the code a human already rejected, the Manager escalates instead of asking again. This three-session behaviour is an automated test.

Zetaris is our data layer, end to end, including the spreadsheet you upload: it becomes a Zetaris REST table, one row per cell, so the data profiler reads it with SQL and the PM joins it with the staff directory that also lives in Zetaris. Zetaris cannot read files on a laptop, so our API serves each table as JSON and we register it as a Lightning REST table: seven statements, sent one at a time after a dry run. Every row count matches the data generator’s manifest. The agents keep writing plain SQL against workforce dot table, and the adapter reads the matching REST table with a lateral view, so we needed no views and no extra database objects. Both the agent’s SQL and the SQL that actually ran are in the trace. We ran all fifteen of the pipeline’s queries on a live local Zetaris, and the findings were identical to sample mode.

Meterless: provider and two engines

Power rule

Nightshift, primary provider

The full provider contract: status from GET /v1/models, auto-detect, connect links, a 180 s timeout. Every call logs the model that answered.

Build rule · engine 1

World Model

Content-hash IDs, an append-only log with row provenance, a 10-step idempotent ingest. Stage 1’s source conflicts are its conflict records.

Build rule · engine 2

H-MEM

Tiered memory behind an approval boundary, 8-signal retrieval with reasons, a hash-chained trust ledger. Approved automations run again without asking.

NVIDIA: Nemotron models run through Nightshift lanes, hosted, with no local GPU. Route used: meterless/deep → nvidia/nemotron-3-ultra-550b-a55b, recorded in every trace.

Meterless appears three times. First, the power rule: Nightshift is our primary model provider, and we implemented its published provider contract: the URL normalization, the status check from the models endpoint, auto-detect, connect links and the long timeout for model loads. Every model call records which model actually answered. Second, the build rule: we implemented two engines from scratch. The World Model is the shared spine every stage reads and writes, and the conflicts our Conflict Critic judges are its own conflict records. H-MEM is the team’s memory, and it changes later decisions: an automation you approved runs again without asking, and one you rejected is not proposed again. NVIDIA Nemotron runs through the Nightshift route meterless deep, which answers with Nemotron 3 Ultra; every trace records it.

What it’s built with

Runtime

Python 3.11, FastAPI, httpx, openpyxl; a plain-JS chat island

State

SQLite for the World Model and H-MEM; JSONL traces

Data

Zetaris 2.4.3 in local Docker, Lightning REST tables

Models

Meterless Nightshift, NVIDIA Nemotron lanes

Packaging

Docker on python:3.11-slim; sample mode needs no keys

Built with

Claude Code; every line reviewed and tested

The stack is deliberately small. Python 3.11 with FastAPI and httpx; no agent framework, the agents are plain Python we wrote. The World Model and H-MEM persist in SQLite, and traces are JSONL. Zetaris runs locally in Docker and holds the data as Lightning REST tables. Models come through Meterless Nightshift, routed to NVIDIA Nemotron. The app ships as a Docker image, and sample mode runs without any keys. We built it with Claude Code, and the team reviewed and tested all of it.
